1. Project Overview

AGNIMARG (Sanskrit for "Path of Fire") is an end-to-end intelligent pipeline designed to protect Indian forests and vulnerable settlements from wildfires. It completely avoids IoT/hardware deployment, relying strictly on remote-sensing, meteorological forecasting, and historical data.

The system is split into two massive interconnected modules:

  • SENTINEL (The Intelligence Module): Uses satellite imagery, weather data, and machine learning to detect existing fires, predict the likelihood of new fires (ignition risk), and simulate how an active fire will spread over the next 24 hours.
  • EXODUS (The Action Module): Takes Sentinel's predictions, places them onto a 3D digital twin of the forest, calculates which villages are in danger, computes the safest evacuation routes avoiding fire-risk zones, and triggers alerts to emergency responders.

Workflow: Data Sources → Ingestion → Sentinel ML → Exodus 3D & Routing → Web Dashboard

Workflow:

Workflow:

  2. JSON response parsed.
  3. Store hourly forecast array in `weather_forecasts` table (JSONB column).
Static GIS Data (DEM, WorldCover) - One Time Setup

Downloaded manually or via scripts to data/raw/. Processed offline into normalized GeoTIFFs stored in data/processed/. Path strings stored in database.

5. Data Preprocessing Pipeline

Raw data is messy. It must be transformed into ML-ready matrices (aligned Rasters) using Python GIS libraries.

  • Reprojection (pyproj/rasterio): All data must be reprojected from EPSG:4326 (Lat/Lon) to a projected CRS (meters) for accurate area/distance calculations. For India, use UTM Zones (e.g., EPSG:32643 or EPSG:32644).
  • Raster Alignment (rioxarray): Sentinel-2 (10m), DEM (30m), and Weather grids (9km) do not align. We use rioxarray.reproject_match() to resample everything to a standard 30m grid.
    - Use Bilinear Interpolation for continuous data (Elevation, Temp, Wind).
    - Use Nearest Neighbor for categorical data (Land Cover classes).
  • Feature Engineering:
    - NDVI = (NIR - Red) / (NIR + Red) (Calculated from Sentinel-2 bands to estimate live fuel moisture).
    - Slope & Aspect derived from DEM using xarray-spatial.slope and aspect.
  • Missing Data: Fill NaN values in rasters with domain-specific defaults (e.g., 0 for wind, mean for elevation) using xr.fillna().

7. Sentinel Module Overview

Sentinel handles all intelligence and prediction. It is strictly divided into four sub-modules to prevent "black box" ML failure.

  1. A. Active Fire Detection: Parses FIRMS satellite thermal anomalies into concrete "Fire Events" via spatial clustering.
  2. B. YOLO Smoke/Fire Image Detection: An optional module for validating early smoke via high-res optical imagery (drone/Sentinel-2 RGB).
  3. C. Ignition-Risk Prediction: A daily XGBoost model predicting where new fires are likely to start based on weather/dryness.
  4. D. Fire-Spread Prediction: A physics-inspired Cellular Automata model running on-demand to forecast the 24-hour boundary of an active fire.
Constraint Check: Do NOT use YOLO for fire spread prediction. Object detection models cannot predict spatial-temporal growth over a terrain.

8. Active Fire Detection (Clustering)

NASA FIRMS gives us raw points (pixels). We must turn pixels into actionable boundaries.

  • Clustering Algorithm: Use DBSCAN from scikit-learn.
  • Parameters: eps=1000 meters (1km radius), min_samples=2.
  • Event Creation: If a cluster of FIRMS points does not spatially intersect a known active polygon in the `fire_events` table (within a 48-hour window), it is treated as a new fire.
  • Polygon Generation: Compute the Convex Hull (`shapely.geometry.MultiPoint(points).convex_hull`) of the cluster. Buffer it by 500m to represent the `current_boundary`.

9. YOLO Fire/Smoke Model

This module uses Computer Vision. It is ONLY used when RGB images (from drones or Sentinel-2 True Color bands) are fed into the system to verify if a heat anomaly is actual fire/smoke or a false positive (like a hot factory roof).

  • Exact Model: Ultralytics YOLO11n (or YOLO11-seg for segmentation). Note: YOLO26 is not a real model; YOLO11 is the current SOTA.
  • Dataset: D-Fire (wildfire smoke/fire bounding boxes).
  • Training Command: 
    yolo train data=dfire.yaml model=yolo11n.pt epochs=50 imgsz=640 batch=16 augment=True
  • Metrics: Precision > 0.8, mAP50-95 > 0.70.
  • Confusion Matrix Goal: Optimize for Recall over Precision (Better to have a false alarm than miss a fire). Minimize False Negatives.

10. Ignition-Risk Model (XGBoost)

A structured ML approach predicting the daily probability of a fire starting in a specific 1km x 1km cell.

  • TARGET: Binary classification (1 = Fire occurred, 0 = No fire).
  • FEATURES (Inputs):
    • Weather (ERA5): Max Temp, Min Humidity, Wind Speed, Precip (lagged 7 days).
    • Terrain (DEM): Elevation, Slope, Aspect.
    • Vegetation (Sentinel-2/WorldCover): NDVI, NDMI (Moisture Index), NBR, Fuel Class (categorical).
    • Human Proximity (OSM): Distance to nearest road, Distance to nearest village.
  • Class Imbalance: Fire pixels are < 0.1% of all forest pixels. Use scale_pos_weight = count(negative_samples) / count(positive_samples).
  • Data Splitting: Crucial. Use Spatial-Temporal Splits.
    - Train: North/Central India forests (2018-2021).
    - Test: South India forests (2022).
    Random splitting causes massive data leakage due to spatial autocorrelation.
  • Metrics: Rely on PR-AUC (Precision-Recall AUC) and Brier Score (for probability calibration). ROC-AUC is misleading in heavily imbalanced geospatial datasets.
  • Output: model.predict_proba() creates a 0.0 to 1.0 risk score mapped back to a GeoTIFF grid.

11. Wildfire Spread Model (Hybrid CA)

Predicting spread requires physics, not just deep learning (which lacks sufficient perfect hourly data in India). We build a Cellular Automata (CA) influenced by the Rothermel fire spread equations.

Mathematical Core: The probability of a burning cell igniting a neighbor is $P_{ignite} = P_{base} imes F_{wind} imes F_{slope} imes F_{fuel}$.
  • Grid Representation: 2D NumPy array representing 30m cells.
  • States: 0 = Unburnable (Water/City), 1 = Unburned Fuel, 2 = Burning, 3 = Burned Out.
  • Neighborhood: Moore (8 surrounding cells).
  • Transition Rules:
    - Wind Factor ($F_{wind}$): $e^{(c \cdot V \cdot \cos( heta))}$ where $V$ is wind speed, $ heta$ is angle between wind direction and the neighbor, $c$ is a calibration constant.
    - Slope Factor ($F_{slope}$): Fire burns faster uphill. $\phi_s = 5.275 an^2(\phi)$.
  • Monte Carlo Simulation: Since wind gusts are stochastic, run the CA simulation 50 times. The percentage of runs where a cell burns becomes its continuous probability (0-100%).
  • Output: A GeoTIFF continuous raster representing the "Spread Risk Surface" over 24 hours.

13. India-Specific Training Dataset Creation

How to construct the tabular dataset for the Ignition Model (XGBoost) for Indian forests.

  1. Positive Samples: Extract centroids of MCD64A1 burned areas in India (2015-2023). Record Date + Lat + Lon.
  2. Negative Samples (Easy): Randomly sample points in Indian forests (via Bhuvan/WorldCover) that did NOT burn.
  3. Hard Negatives: Sample points near roads or dry clearings during extreme summer heat that did not burn. Forces the model to learn subtle fuel limits, not just "summer = fire".
  4. Data Merging: For every point/date, query ERA5 for weather on that date, and query the DEM for slope/aspect. Construct a flat CSV for XGBoost.

15. Exodus 3D System

Exodus uses CesiumJS to create an interactive 3D digital twin.

  1. Terrain: Convert Copernicus DEM GeoTIFF to Cesium Quantized Mesh using cesium-terrain-builder, or serve via Mapbox/Cesium ion.
  2. Base Imagery: Use Bing Maps Aerial or ISRO Bhuvan WMS (if accessible).
  3. Vector Overlays: Load villages and roads from the Flask API. Display villages as 3D Billboards (markers).
  4. Fire Rendering: Convert the active current_boundary to a glowing Cesium Polygon entity draped over the 3D terrain using ClassificationType.TERRAIN.

16. 3D Heatmap Rendering

Sentinel's array output must become a 3D overlay in Exodus:

  1. Python CA outputs a 2D NumPy array of probabilities.
  2. rasterio writes this array to a GeoTIFF, assigning the local CRS and bounds.
  3. Flask API serves this GeoTIFF as an Image or via a local WMS layer.
  4. CesiumJS loads it via SingleTileImageryProvider.
  5. Apply a Color Ramp: 0-20% = Transparent. 20-50% = Yellow (alpha 0.4). 50-80% = Orange. 80-100% = Red (alpha 0.8).

17. Evacuation Routing

Using OSMnx and NetworkX in the Python backend to build dynamic safe routes.

  1. Graph Extraction: Download the District road network: G = ox.graph_from_polygon(study_area, network_type='drive').
  2. Threat Detection: Intersect villages geometries with the >50% fire probability raster. If intersection > 0, village is "Threatened".
  3. Dynamic Edge Weighting: Standard routing uses shortest path (distance). We use a Risk-Aware Cost Equation.
Cost Equation: $Cost_{edge} = rac{Length}{Speed} + (Penalty imes FireRisk_{edge})$
If $FireRisk_{edge} > 0.8$, the edge is completely removed from the graph (road is blocked/impassable).
  1. Routing: Run A* (nx.astar_path) from the Threatened Village to the nearest Safe Shelter.
  2. Delivery: Export the path to GeoJSON LineString. CesiumJS renders it as a glowing green line routing *around* the red fire zone.

25. Testing Strategy

  • Unit Tests (pytest): Test math functions. Is the slope factor calculating correctly?
  • GIS Validation: Ensure inputs to ML are strictly Lat/Lon or strictly UTM. Prevent coordinate axis inversion.
  • Calibration: Check Brier Score for XGBoost. If the model outputs 80% risk, does fire actually happen 80% of the time in those conditions?
  • Route Safety Check: Write a test that artificially places a massive fire blob over the shortest path; assert that OSMnx successfully routes the long way around.

27. Risks & Limitations (For Presentation Honesty)

  • Resolution: Sentinel-2 is 10m, but thermal data (VIIRS) is 375m. Small fires (<10m) might be missed.
  • Cloud Cover: Satellites cannot see through thick clouds (except SAR, which is complex for thermal).
  • Wind Micro-climates: 9km ERA5 wind data does not capture small valley breezes, leading to CA spread uncertainty.
  • Ground Truth: Direct validation of the exact minute a fire starts is impossible without IoT; we rely on satellite revisit times.
